## Deviations

- `observations` is `null` when a beach has no usable observation rows (8 of 850 on this snapshot), where the API returns 404. The contract's client rule falls back to the API on a null section.
- `explain` is null for the 354 beaches with no forecast row (850 − 496), matching the API's 404/stale behaviour.
- `health.json` keeps the extra research keys. The API's response model drops them. They validate and the web research page needs them.

## Open questions

- Size: `beach/` is ~31 MB for 850 files (~28 KB each), almost all of it the per-cell `hourly` payload repeated for every beach in a cell. Pages should handle it. If the web deploy cares, an `hourly/{cell}.json` would shrink it, but that changes the contract.
- `tides` is null for 66 beaches. These are mostly beaches nearest to the 3 stations that failed in phase 50 (9410665, 9413745, 9415118), plus any beach with no coordinates.
- Pre-existing, unchanged: the baker's forecast block does not apply the serve-time confidence cap that the API applies to unposted beaches on samples older than 60 days. `explain` inherits the baker's band and probability, so it can differ from `BeachService` in that rare case.
- Pre-existing, for phase 100: the existing `beaches.json` rows are the web's flat shape (`id`, `latitude`, `longitude`, ...), not `BeachSummary` (`geometry`, ...). The brief asks the parity test to validate them against `BeachSummary`. That will fail, or need an adapter, unless the contract means something else.
